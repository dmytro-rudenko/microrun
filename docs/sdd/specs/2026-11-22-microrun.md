# microrun — безпечний відкат релізів для Docker Compose — design

**Date:** 2026-11-22
**Status:** agreed
**Prototype:** docs/sdd/proto/microrun-ui/decision.md
**Source:** бізнес-ТЗ «Інструмент безпечного відкату релізів» (робоча назва «мікро-Ранчер»), 22.11.2026

## 1. Problem

Проєкти на Docker без Kubernetes деплоять з CI/CD гілки (`prod`, `stage`, `dev`) і не мають
безпечного способу повернути попередній реліз. Сьогодні відкат означає одне з двох:

- передеплоїти старий коміт — але міграції нового релізу вже змінили схему, і старий код
  може не запуститися або зламатися на ній;
- відновити БД з бекапу — і втратити всі дані користувачів, записані після деплою.

Навіть успішний ручний відкат не захищає від повтору: гілка `prod` усе ще містить зламаний
коміт, і перезапуск того самого пайплайну знову викатує його на продакшн.

## 2. Constraint that shapes the solution

**Відкат не може змінювати схему БД і не може торкатися даних.** Тільки так він вкладається
в 1 хвилину й гарантує, що дані в полях, які існували до релізу, не втрачаються. Звідси:

- Схема кожного релізу має бути *надмножиною* схеми попереднього (expand/contract): міграції
  під час деплою лише додають, а видалення відкладене до закінчення вікна зберігання.
  Тоді старий код працює на новій схемі, і відкат — це тільки заміна образу.
- Очевидна альтернатива — `down`-міграції під час відкату — відкинута: вони повільні,
  знищують дані з нових колонок і залежать від того, чи розробник їх правильно написав.
- Друга альтернатива — інструмент сам підтримує подвійну схему (shadow-таблиці, тригери,
  як pgroll) — відкинута: окрема реалізація для кожної з чотирьох СУБД і втручання в DDL
  застосунку.
- Дисципліну expand/contract не можна довіряти людям, тому microrun **перевіряє її машиною**:
  на production — dry-run міграцій на копії схеми до того, як вони торкнуться справжньої бази;
  на інших оточеннях — порівняння схеми після міграції до заміни контейнерів.

Друге обмеження — **гейт деплою має бути неминучим**. Тому деплой виконує сам microrun (CI лише
викликає `microrun deploy`), а не спостерігає за деплоєм, який CI робить сам: пропущений крок
перевірки в пайплайні інакше обходив би блокування.

## 3. Solution

### 3.1 Glossary

| Термін | Значення |
|---|---|
| Оточення (environment) | Іменована зв'язка: гілка репозиторію + сервер + compose-проєкт і сервіси + база даних + налаштування сховища й вікна. |
| Реліз (release) | Один коміт гілки оточення, викатаний на оточення: образи сервісів (карта сервіс → ref + digest), коміт, автор, повідомлення, час, знімок і diff схеми. Належить рівно одному оточенню. |
| Новіший / старший реліз | Для відкату — за `activation_seq` (порядок активацій в оточенні); для contract — за `deployed_at` першого успішного деплою (порядок еволюції схеми). |
| Активний реліз | Той, що зараз працює. Рівно один на оточення. |
| Доступний реліз | Колишній активний, вікно зберігання якого ще не минуло; ціль для відкату. |
| Заблокований реліз | Реліз, з якого (або через який) виконано відкат. Повторний деплой його коміту відхиляється. |
| Прострочений реліз | Реліз, вікно якого минуло; образ видалено, відкат неможливий. |
| Вікно зберігання (retention) | Тривалість, протягом якої реліз після заміни новішим лишається доступним для відкату. Налаштовується на оточення. |
| Expand / contract | Дві команди міграцій застосунку: expand лише додає (виконується під час деплою), contract видаляє застаріле (виконується після закінчення вікна). |
| Маркер оточення | Таблиця/колекція `_microrun_env` у базі оточення з ідентифікатором оточення, якому база належить. |
| Агент | Процес на сервері з Docker, який підключається до microrun вихідним WebSocket і виконує його команди. |
| Операція (operation) | Один запис історії: деплой, відкат, прибирання, contract або закінчення вікна. |

### 3.2 Components

Монорепозиторій pnpm workspaces. Node.js 26 LTS, TypeScript (актуальний стабільний, `strict`),
ESM. Ліцензія open-source (MIT — *моє рішення*).

| `packages/server` → Docker-образ `microrun/microrun` | Fastify: веб-UI (SSR + htmx), CI API, WebSocket-хаб агентів, планувальник, SQLite через knex (`better-sqlite3`). Якщо змонтовано `/var/run/docker.sock` — запускає вбудований агент для локального сервера. | `docker run` / compose (див. 3.13). | `core`, `agent` (як бібліотеку для вбудованого агента), `fastify`, `knex`, `better-sqlite3` |
| `packages/agent` → npm-пакет `microrun` | Bin `microrun` з підкомандами `agent` (демон на сервері) і `deploy` (для CI). | `npm i -g microrun` / `pnpm add -g microrun` / `yarn global add microrun`. | `core`, Docker CLI з плагіном compose на хості |

Назва Docker-образу `microrun/microrun` і npm-пакета `microrun` — *моє рішення*, змінюються
до першого релізу без впливу на дизайн.

### 3.3 Data model (SQLite, міграції knex у `packages/server/migrations`)

```
servers
  id text pk (uuid) · name text unique · agent_token_hash text · builtin int(0/1)
  proxy_mode text check in ('external','bundled') default 'external'
  last_seen_at int null · agent_version text null

environments
  id text pk (uuid) · name text unique · branch text unique · is_production int · position int
  server_id text fk servers
  compose_project text · compose_dir text · compose_files text(json array)
  services text(json: [{name, strategy: 'rolling'|'recreate', domain?, port?}])
  migration_service text            -- сервіс, з образу й env якого виконуються міграції
  db_kind text check in ('postgres','mysql','sqlite','mongodb')
  db_url_env text                   -- ім'я змінної оточення з URL бази, напр. DATABASE_URL
  db_marker_id text unique null     -- uuid у _microrun_env; null до прив'язки бази
  migration_tables text(json array) -- таблиці/колекції історії міграцій для dry-run
  expand_cmd text · contract_cmd text null · cleanup_cmd text null
  schema_check text check in ('dry_run','post_check')
  health_timeout_s int default 120
  storage_kind text check in ('local','registry','s3') · storage_config_enc blob
  retention_s int check >= 3600
  deploy_token_hash text

releases
  id text pk · env_id text fk · commit_sha text
  images text(json: {<service>: {ref, digest}})   -- рівно сервіси оточення
  author text · message text · deployed_at int · superseded_at int null
  activation_seq int null           -- monotonic лічильник активацій в оточенні
  schema_snapshot text(json) · schema_diff text(json)
  state text check in ('active','available','blocked','expired','failed')
  destructive_approved int(0/1) default 0
  cleanup_state text check in ('none','pending','applied','dismissed','lapsed') default 'none'
  cleanup_preview text(json) null
  blocked_at int null · blocked_by_op text null fk operations
  stored int(0/1) · image_purged_at int null · contracted_at int null
  unique(env_id, commit_sha)
  partial unique index on (env_id) where state = 'active'

operations
  id text pk · env_id text fk · kind text check in ('deploy','rollback','cleanup','contract','expire')
  from_release_id text null · to_release_id text null
  actor text                        -- 'admin' | 'system' | 'ci:<author>'
  status text check in ('pending','running','succeeded','failed','rejected')
  code text null                    -- стабільний код результату (3.6)
  params text(json) null            -- параметри для локалізованого повідомлення
  log text · steps_done text(json)  -- підтверджені кроки для відновлення
  cleanup_result text(json) null
  started_at int · finished_at int null
  partial unique index on (env_id) where status in ('pending','running')

destructive_approvals
  env_id text fk · commit_sha text · diff text(json) · approved_at int · used_by_op text null
  primary key (env_id, commit_sha)

sessions
  id text pk · created_at int · expires_at int
```

Час — Unix ms. Структура робить неможливими два активні релізи на оточенні й дві одночасні
операції на оточенні — перевірка не в коді, а в індексах. Секрети сховищ шифруються
AES-256-GCM ключем `MICRORUN_SECRET_KEY`; токени зберігаються тільки як SHA-256-хеші
(токени — 32 випадкові байти, base64url, тож повільний хеш не потрібен).

### 3.4 Release state machine (core, чиста функція)

```
deploy ok:            (new) → active (activation_seq = max + 1); previous active → available (superseded_at = now)
deploy failed:        (new) → failed;           previous active лишається active
rollback to T:        current active і всі available з activation_seq > T.activation_seq → blocked;
                      потім T → active (activation_seq = max + 1)
expire:               available → expired       (now − superseded_at ≥ retention)
manual window close:  усі available, старші за R → expired
```

`blocked` і `expired` — кінцеві для відкату. `blocked` — кінцевий назавжди: закінчення вікна видаляє образ заблокованого релізу (`image_purged_at`), але стан лишається `blocked`, тож коміт не можна задеплоїти повторно ніколи. Повторний деплой коміту:

| Стан коміту в цьому оточенні | Результат `deploy` |
|---|---|
| немає | звичайний деплой, новий реліз |
| `active` | нічого не робить, успіх (`ALREADY_ACTIVE`) — *моє рішення* |
| `available` | реактивація: без expand (схема й так надмножина), заміна образу, попередній активний → `available` |
| `blocked` | відмова `COMMIT_BLOCKED` |
| `failed` | повний деплой; рядок релізу оновлюється на місці |
| `expired` | відмова `COMMIT_EXPIRED`: після закінчення вікна contract новіших релізів міг видалити те, що цьому коду потрібно — *моє рішення* |

Деплой `available`-коміту через CI (реактивація) нічого не блокує — блокування робить тільки
відкат з UI. Коміт, якого microrun ще не бачив, завжди вважається новим: microrun не знає графа
git, тож старий невідомий коміт або пайплайн, що завершився не по черзі, деплояться як нові
(див. 5).

Блокування прив'язане до пари (оточення, коміт): коміт, заблокований на production,
деплоїться на stage як завжди.

### 3.5 Deploy flow

1. CI: `microrun deploy --url $MICRORUN_URL --token $MICRORUN_DEPLOY_TOKEN --image <svc>=<ref> [--image <svc>=<ref> …] --commit <sha> --branch <branch> [--author <name>] [--message <text>]`.
   Один `--image <ref>` без `<svc>=` застосовується до всіх сервісів оточення; інакше карта має
   покривати рівно всі сервіси оточення (`INVALID_REQUEST`). Міграції й cleanup виконуються з
   образу сервісу `migration_service`. Автор і повідомлення типово беруться з `git log -1`.
2. Сервер `POST /api/v1/deploy` (Bearer deploy-токен визначає оточення) перевіряє і **відхиляє до
   будь-яких змін** з кодом і локалізованим повідомленням:
   `BRANCH_MISMATCH`, `COMMIT_BLOCKED`, `COMMIT_EXPIRED`, `AGENT_OFFLINE`, `ENV_BUSY`, `DB_NOT_BOUND`,
   `INVALID_REQUEST`.
   Інакше створює операцію `deploy` у статусі `pending` і повертає `202 {operationId}`.
3. Агент виконує кроки (кожен — ідемпотентна команда з ключем `(operation_id, step)`):
   1. `pull` усіх образів релізу; далі сервіси запускаються за digest (облікові дані registry
      застосунку — з `docker login` хоста; для вбудованого агента — змонтований `~/.docker/config.json`).
   2. Перевірка маркерів: база в `db_url_env` кожного сервісу оточення має маркер цього
      оточення, інакше `DB_MARKER_MISMATCH`.
   3. Базова схема — `schema_snapshot` активного релізу; якщо активного немає (перший деплой
      після підключення) — живий знімок бази (3.8).
   4. Якщо `schema_check = dry_run`: тимчасовий контейнер тієї самої СУБД і мажорної версії
      (`microrun-dryrun-<op>`), у нього — schema-only dump і **дані** таблиць
      `migration_tables`; `expand_cmd` з нового образу з `db_url_env`, що вказує на тимчасову
      базу; знімок → diff з базовою схемою. Деструктивна зміна → `SCHEMA_DESTRUCTIVE`, справжня
      база не зачеплена (якщо немає дозволу, 3.5а).
      Тимчасовий контейнер видаляється в будь-якому разі.
   5. `expand_cmd` на справжній базі (одноразовий контейнер з образу й env сервісу
      `migration_service`, у compose-мережі проєкту). Ненульовий код → `MIGRATION_FAILED`.
   6. Знімок `after` → `schema_snapshot` і diff з базовою схемою зберігаються в релізі. Якщо
      `post_check` і diff деструктивний без дозволу → `SCHEMA_DESTRUCTIVE` (у повідомленні: зміна
      вже застосована до бази). Порівняння з базовою схемою, а не з живою базою, означає, що
      повторний запуск того самого коміту не проходить мовчки.
   7. Заміна сервісів (3.7). Health не пройдено за `health_timeout_s` → `HEALTHCHECK_FAILED`,
      старі контейнери не зупиняються (rolling) або повертаються на попередній образ (recreate).
   8. Реліз → `active`, попередній → `available`. Локальна копія образу закріплюється.
   9. Копіювання образу у сховище (3.10). Збій не скасовує деплой: `stored = 0`,
      попередження в UI, планувальник повторює.
4. Невдалий крок 3.x → реліз `failed`, операція `failed` з кодом. `expand` не відкочується —
   він лише додає, тож попередній реліз працює далі.
5. CLI слухає `GET /api/v1/operations/:id/events` (SSE), друкує кроки й завершується:

| Exit code | Коли |
|---|---|
| 0 | `succeeded` або `ALREADY_ACTIVE` |
| 1 | `failed` (`MIGRATION_FAILED`, `HEALTHCHECK_FAILED`, `IMAGE_PULL_FAILED`, …) |
| 2 | `rejected` політикою (`COMMIT_BLOCKED`, `COMMIT_EXPIRED`, `BRANCH_MISMATCH`, `SCHEMA_DESTRUCTIVE`, `DB_MARKER_MISMATCH`, `DB_NOT_BOUND`, `INVALID_REQUEST`) |
| 3 | сервер недоступний, невірний токен, `ENV_BUSY` після `--busy-timeout` (типово 600 с; CLI повторює кожні 10 с), `AGENT_OFFLINE` |

Повідомлення для `COMMIT_BLOCKED` (uk): «Коміт `<sha>` заблоковано на `<env>`: з нього виконано
відкат `<дата>`. Зробіть новий коміт із виправленням і задеплойте його.»

### 3.5a Approving a destructive schema change

Обхід гейту існує тільки в UI; CI сам його отримати не може.

1. Операція, відхилена з `SCHEMA_DESTRUCTIVE`, у панелі історії й оточення має кнопку
   «Дозволити для коміту `<sha>`». Діалог показує деструктивні рядки diff і перелік доступних
   релізів, які **стануть прострочені** (їхній код може залежати від видаленого). Для будь-якого
   оточення треба ввести його назву.
2. Підтвердження пише `destructive_approvals(env_id, commit_sha, diff)` і операцію історії.
3. Наступний `deploy` цього коміту проходить гейт, якщо фактичний деструктивний diff збігається
   зі схваленим (інакше — знову `SCHEMA_DESTRUCTIVE`); дозвіл одноразовий (`used_by_op`).
   Після успіху реліз має `destructive_approved = 1`, а всі `available` релізи оточення →
   `expired`, тож відкат на код, несумісний зі схемою, неможливий.

### 3.6 Result codes and messages

Стабільні коди (англ. `UPPER_SNAKE`) — частина API; повідомлення до них — у каталогах i18n
(3.12). API повертає `{code, message, params}`, `message` локалізоване за `Accept-Language`.
Повний перелік: `ALREADY_ACTIVE`, `BRANCH_MISMATCH`, `COMMIT_BLOCKED`, `COMMIT_EXPIRED`,
`SCHEMA_DESTRUCTIVE_APPROVED`, `AGENT_OFFLINE`,
`ENV_BUSY`, `DB_NOT_BOUND`, `DB_MARKER_MISMATCH`, `IMAGE_PULL_FAILED`, `SCHEMA_DESTRUCTIVE`,
`MIGRATION_FAILED`, `HEALTHCHECK_FAILED`, `AGENT_LOST`, `CLEANUP_MISMATCH`, `CONTRACT_FAILED`,
`STORAGE_FAILED`, `INVALID_REQUEST`, `UNAUTHORIZED`.

### 3.7 Service switch (zero-downtime)

Для кожного оточення microrun пише override-файл `<compose_dir>/docker-compose.microrun.yml`
з `services.<svc>.image: <ref>@<digest>` для кожного сервісу оточення з карти `images` релізу і викликає compose з
`-f <compose_files…> -f docker-compose.microrun.yml -p <compose_project>`.

- `rolling` (N реплік): `up -d --no-deps --no-recreate --scale <svc>=2N <svc>` → чекати, поки
  нові N контейнерів `healthy` → `stop` + `rm` старих N. Старі не зупиняються, доки нові не
  здорові, тож невдала заміна не створює простою.
  - `proxy_mode = external`: трафік розподіляє proxy проєкту (Traefik, nginx-proxy,
    caddy-docker-proxy, nginx із Docker DNS) — microrun його не чіпає.
  - `proxy_mode = bundled`: агент тримає контейнер `microrun-proxy` (Caddy) на цьому сервері,
    підключений до мереж обслуговуваних проєктів; маршрути `domain → svc:port` з налаштувань
    сервісу; під час заміни агент через admin API Caddy додає нові upstream, чекає health,
    прибирає старі. TLS — автоматичний Caddy.
- `recreate`: `up -d --no-deps <svc>` → чекати `healthy` (якщо є healthcheck) або `running`
  10 с. Для воркерів і кронів, де трафіку немає.

Вимоги до `rolling`-сервісу перевіряються під час збереження оточення і блокують збереження:
є `healthcheck`, немає `container_name`, немає портів, прив'язаних до хоста.

### 3.8 Schema snapshot and diff

Агент знімає схему одноразовим клієнтським контейнером у compose-мережі проєкту
(`postgres:<major>`, `mysql:<major>`, `mongo:<major>`, `keinos/sqlite3` з примонтованим томом
бази — *моє рішення щодо образу sqlite*). URL бази — зі змінної `db_url_env` сервісу
`migration_service` за `docker compose config`; microrun не зберігає облікових даних БД.

Типи нормалізуються до канонічної форми СУБД перед порівнянням (Postgres — `format_type()` з
`pg_catalog`, MySQL — `COLUMN_TYPE`, SQLite — affinity, `character varying` ≡ `varchar`);
default-вирази порівнюються після нормалізації пробілів і приведень типу. Помилкові спрацювання,
які все ж трапляться, закриває дозвіл 3.5а.

Нормалізований знімок (core):

```
SQL:   tables[{name, columns[{name, type, nullable, default}], indexes[{name, columns, unique}]}]
Mongo: collections[{name, indexes[{name, keys, unique}], validator}]
```

Класифікатор diff (core, чиста функція) повертає `[{kind: 'add'|'warn'|'drop', object, detail}]`:

| Зміна | Клас |
|---|---|
| нова таблиця/колекція, нова nullable-колонка, нова `NOT NULL` з default, новий неунікальний індекс | `add` |
| розширення типу з білого списку: `varchar(n)→varchar(m>n)`, `varchar→text`, `int→bigint`, `smallint→int`, збільшення точності `numeric` | `add` |
| новий unique-індекс, посилений Mongo-валідатор, видалений індекс | `warn` |
| видалена таблиця/колекція/колонка, перейменування (= drop + add), будь-яка інша зміна типу, nullable → `NOT NULL`, нова `NOT NULL` без default | `drop` (деструктивна) |

Деструктивна — будь-яка `drop`. `warn` показується в UI і в логах CLI, деплой не зупиняє.

Dry-run: Postgres — `pg_dump --schema-only` + `pg_dump --data-only -t <migration_tables>`;
MySQL — `mysqldump --no-data` + дані `migration_tables`; SQLite — `.schema` + дані
`migration_tables` у тимчасовий файл; MongoDB — колекції з індексами й валідаторами + документи
`migration_tables`. Типові `migration_tables`, якщо поле порожнє: `knex_migrations`,
`knex_migrations_lock`, `_prisma_migrations`, `migrations`, `typeorm_metadata`,
`SequelizeMeta`, `schema_migrations`, `flyway_schema_history`, `changelog` — ті, що існують.

### 3.9 Rollback flow

1. UI: адміністратор відкриває доступний реліз T (картка на головній або рядок таблиці на
   сторінці оточення) → бічна панель показує, які релізи буде заблоковано, і що схема не
   змінюється. Для production кнопка активна тільки після введення назви оточення.
2. Сервер створює операцію `rollback`; ті самі перевірки `AGENT_OFFLINE`, `ENV_BUSY`.
3. Агент: образи T з локальних закріплених копій (яких немає — зі сховища) → заміна
   сервісів (3.7) з `health_timeout_s = min(налаштування, 45)`. DDL не виконується.
4. Транзакція в SQLite: T → `active`; поточний активний і всі `available`, новіші за T, →
   `blocked` (`blocked_by_op`). Операція `succeeded`.
5. Невдала заміна → операція `failed`, стани релізів не змінюються, старі контейнери працюють.

Ціль ≤ 60 с досяжна, бо образи всіх доступних релізів завжди лежать на хості (не видаляються
до закінчення вікна) і DDL не виконується.

**Прибирання даних** — окремий крок після успішного відкату, ніколи не затримує сам відкат
і не тримає оточення зайнятим, поки адміністратор думає:

0. Кожен реліз з `cleanup_cmd`, заблокований цим відкатом, отримує `cleanup_state = 'pending'`.
   Прогін `--dry-run` і прогін `--apply` — це дві окремі короткі операції `cleanup`; попередній
   перегляд зберігається в `releases.cleanup_preview`, тож між ними деплої й відкати не
   блокуються. «Не прибирати» → `dismissed`; після `--apply` → `applied`; образ релізу видалено
   до рішення → `lapsed`.
1. Для кожного заблокованого цим відкатом релізу з `cleanup_cmd` (від новішого до старішого)
   агент запускає `<cleanup_cmd> --dry-run` з **образу цього релізу** з env сервісу
   `migration_service` і змінними `MICRORUN_ENV`, `MICRORUN_RELEASE_COMMIT`,
   `MICRORUN_DEPLOYED_AT`, `MICRORUN_ROLLED_BACK_AT` (ISO 8601 UTC).
2. Протокол stdout — JSON-рядки; інші рядки йдуть у лог:
   - `--dry-run`: `{"rule": "<id>", "description": "<text>", "count": <int>}`
   - `--apply --rules=<id>,<id>`: `{"rule": "<id>", "deleted": <int>}`
3. UI показує правила з кількістю й чекбоксами (правила з `count = 0` неактивні), кнопка
   «Видалити N записів». «Не прибирати» завершує крок без змін.
4. Після `--apply` в історію пишуться обидва числа; розбіжність → попередження
   `CLEANUP_MISMATCH` в історії й у панелі.
5. Прибирання заблокованого релізу можна запустити й пізніше з його панелі, поки
   `image_purged_at IS NULL`.

### 3.10 Retention, expiry, contract, storage

Планувальник (у процесі сервера, кожні 60 с):

- `available`, у яких `now − superseded_at ≥ retention_s` → `expired` (операція `expire`,
  actor `system`).
- `blocked`, у яких `now − blocked_at ≥ retention_s`, лишаються `blocked`; видаляється лише їхній образ.
- Для прострочених і таких заблокованих: видалити образ зі сховища і з хоста (`docker rmi`, якщо
  не використовується), `image_purged_at = now`. Агент офлайн → повтор на наступному тіку.
- **Contract.** Для кожного не-`blocked`, не-`failed` релізу R з `contract_cmd` і
  `contracted_at IS NULL`: якщо всі релізи цього оточення, старші за R (за `deployed_at`), мають
  стан `expired`, `blocked` або `failed`, і жоден із них не має `cleanup_state = 'pending'`
  (cleanup може потребувати колонок, які contract видалить) — операція `contract`: `contract_cmd` з образу R
  (env `migration_service`), потім `contracted_at = now`. Обробляються в хронологічному порядку,
  по одному за тік на оточення. Збій → `CONTRACT_FAILED`, попередження в UI, кнопка
  «Повторити»; автоматично не повторюється.
- Розробник тримає contract-міграції окремо від expand (окрема команда/каталог); contract R
  містить лише видалення того, що R уже не використовує.
- **Вручну:** «Завершити вікно для R» в панелі релізу → підтвердження зі списком релізів, що
  стануть `expired` → вони `expired`, далі contract R як вище.

Сховища (на оточення, `storage_config` зашифровано):

| `storage_kind` | Конфігурація | Збереження образу |
|---|---|---|
| `local` | `path` на хості агента | `docker save <refs…> \| gzip > <path>/<env>/<sha>.tar.gz` (усі образи релізу в одному архіві) |
| `registry` | `registry`, `repository`, `username`, `password` | `docker tag` + `push <registry>/<repository>:<env>-<sha>-<svc>` для кожного образу |
| `s3` | `endpoint`, `region`, `bucket`, `prefix`, `access_key`, `secret_key`, `force_path_style` | `docker save \| gzip` → multipart upload `<prefix>/<env>/<sha>.tar.gz` |

Сховище — резервна копія; швидкий шлях відкату — закріплена локальна копія образу.

### 3.11 Environments, database binding, agents

- **Гілка → оточення** — `environments.branch` (unique); `deploy` перевіряє збіг.
- **Прив'язка бази** («Перевірити й прив'язати» в редакторі оточення): агент читає URL з
  `db_url_env` сервісу `migration_service`, з клієнтського контейнера читає `_microrun_env`.
  Немає маркера → створює `_microrun_env(env_id text, env_name text, bound_at text)` з одним
  рядком (Mongo — колекція з одним документом) і зберігає `db_marker_id`. Маркер іншого
  оточення → відмова з назвою того оточення. Маркер цього ж оточення → ок (повторна прив'язка
  ідемпотентна).
- **Чужа база в контейнері:** агент кожні 5 хв і перед кожним деплоєм читає маркер бази з
  `db_url_env` кожного сервісу оточення (сервіси без цієї змінної пропускаються). Розбіжність →
  попередження на головній і сторінці оточення («Сервіс X підключений до бази з маркером
  оточення Y») і відмова `DB_MARKER_MISMATCH` для деплою та відкату.
- **Агент:** `microrun agent --url <MICRORUN_URL> --token <AGENT_TOKEN>` (або
  `MICRORUN_URL`/`MICRORUN_AGENT_TOKEN`). Вихідний WebSocket `wss://<host>/api/v1/agent`,
  heartbeat 15 с, reconnect з експоненційним backoff до 30 с. Handshake передає
  `protocolVersion`; несумісна мажорна версія → сервер закриває з'єднання з поясненням.
  Вхідні порти й SSH не потрібні. Встановлення як systemd-сервіс — команда
  `microrun agent install-service` друкує unit-файл (*моє рішення*).
- **Вбудований агент:** якщо в контейнер сервера змонтовано `docker.sock`, сервер реєструє
  сервер `builtin = 1` і виконує команди тим самим кодом агента в процесі.
- **Агент зник посеред операції:** операція чекає reconnect 5 хв і продовжує з першого
  непідтвердженого кроку (`steps_done`); інакше `failed` з `AGENT_LOST`.
- **Перезапуск сервера:** операції `pending`/`running` продовжуються з `steps_done`.

### 3.12 Web UI and i18n

Затверджено прототипом (див. decision.md, варіант D2). SSR-шаблони на сервері + htmx для
часткових оновлень; хід операції — SSE. Екрани:

- `/login` — логін і пароль з `MICRORUN_ADMIN_USER` / `MICRORUN_ADMIN_PASSWORD`.
- `/` — колонки оточень (порядок — за полем `position` редактора; production з червоною
  рамкою й тегом `PRODUCTION`); у колонці — гілка, вікно, стан агента, попередження, таймлайн
  релізів (стан, автор, відносний час, смужка й текст залишку вікна).
- `/env/:id` — метадані оточення, попередження, таблиця релізів (реліз, стан, зміни схеми,
  вікно).
- Бічна панель релізу (відкривається з `/` і `/env/:id`): деталі, diff схеми, нотатки,
  відкат (3.9), хід кроків, прибирання даних, «Завершити вікно». На ширині ≥ 1100 px вона
  зсуває вміст, а не перекриває його.
- `/history` — таблиця операцій з фільтром за оточенням; причина відмови/збою під статусом.
- `/settings/servers` — сервери й агенти: створення (показує токен один раз і команду
  встановлення), стан, перевипуск токена, `proxy_mode`.
- `/settings/env/:id` — редактор оточення (усі поля 3.3), «Перевірити й прив'язати базу»,
  перевипуск deploy-токена, вимоги rolling (3.7).
- Тема світла/темна за `prefers-color-scheme`. Без горизонтальної прокрутки від 360 px.

Безпека UI: сесійна cookie `httpOnly`, `SameSite=Strict`, `Secure`, якщо `MICRORUN_PUBLIC_URL`
— https; сесія 12 год; CSRF-токен у кожному не-GET запиті (htmx `hx-headers`); пароль
порівнюється за сталий час; вхід — не більше 5 спроб за хвилину з IP; усі дані користувача
екрануються шаблонізатором.

**i18n.** Мови: `uk`, `en`, `de`, `fr`, `es`, `pt-BR`, `pl`, `zh-CN`. Каталоги —
`packages/core/src/i18n/<lang>.json`, ключі ідентичні в усіх мовах (тест), відсутній ключ →
`en`. Множина через `Intl.PluralRules`, числа, дати, тривалості й відносний час — через
`Intl`. Мова UI: cookie `mr_lang` (перемикач у шапці) → `Accept-Language` → `en`. Мова CLI:
`--lang` → `LC_ALL`/`LANG` → `en`; CLI шле її серверу в `Accept-Language`. Дані користувача
(повідомлення комітів, описи правил, назви) не перекладаються. Параметри повідомлень
екрануються під час підстановки.

### 3.13 Installation and configuration

```yaml
# docker-compose.yml для microrun
services:
  microrun:
    image: microrun/microrun:1
    restart: unless-stopped
    env_file: .env
    ports: ["8080:8080"]
    volumes:
      - microrun-data:/data
      - /var/run/docker.sock:/var/run/docker.sock   # вмикає вбудований агент
volumes:
  microrun-data:
```

| ENV | Обов'язкова | Значення |
|---|---|---|
| `MICRORUN_ADMIN_USER` | так | логін адміністратора |
| `MICRORUN_ADMIN_PASSWORD` | так | пароль, ≥ 12 символів, інакше сервер не стартує |
| `MICRORUN_SECRET_KEY` | так | 32 байти base64 для шифрування секретів |
| `MICRORUN_PUBLIC_URL` | так | зовнішній URL (для команд установки агента й `Secure` cookie) |
| `MICRORUN_DATA_DIR` | ні | `/data`; SQLite `microrun.db` у WAL-режимі |
| `PORT` | ні | `8080` |

Вбудований агент, якщо `docker.sock` змонтовано, потребує доступу до `compose_dir` проєктів —
ці каталоги монтуються в контейнер за тим самим шляхом (документація встановлення).

### 3.14 Testing

- `core` — unit (vitest): класифікатор diff (кожен рядок таблиці 3.8), машина станів і
  таблиця повторного деплою 3.4, правило contract 3.10, розрахунок вікна, `t()` і множина,
  ідентичність ключів у 8 каталогах.
- `server` — інтеграційні (vitest, SQLite in-memory, фейковий агент на протоколі core):
  гейти `deploy` з усіма кодами 3.6, відкат через кілька релізів (блокує всі новіші),
  неможливість другої операції й другого активного релізу, `COMMIT_EXPIRED`, дозвіл
  деструктивної зміни (одноразовий, збіг diff, прострочення доступних), прибирання не тримає
  оточення зайнятим, contract чекає `pending`-прибирання, кілька образів на реліз, відновлення після перезапуску,
  планувальник expire/contract, автентифікація й CSRF.
- `agent` — інтеграційні на справжньому Docker (`pnpm test:docker`): compose-фікстура
  застосунку з Postgres, MySQL, MongoDB і SQLite; dry-run відхиляє drop-колонку, не торкнувшись
  бази; rolling без простою (безперервні HTTP-запити під час заміни — 0 помилок); маркери.
- e2e (`pnpm test:e2e`, Playwright + Docker): CI-деплой v1 → v2 (додає колонку) → запис даних
  у старі й нові поля → відкат з UI → ≤ 60 с, дані в старих полях на місці → повторний
  `microrun deploy` v2 → exit 2 `COMMIT_BLOCKED` → v3 деплоїться звичайно; прибирання з
  підтвердженням; production вимагає введення назви; 8 мов без сирих ключів.

## 4. Out of scope

- Kubernetes, Docker Swarm, застосунки не на Docker Compose.
- Відновлення БД з бекапу; `down`-міграції.
- Автоматичне визначення «поганих» даних — правила прибирання пише розробник.
- Відкат зовнішніх наслідків (листи, пуші, платежі).
- Ролі, кілька користувачів, SSO; Cloud-версія; сповіщення (Slack, Telegram); окремий журнал аудиту поза історією операцій.
- Виявлення змін структури всередині документів MongoDB (перейменування полів у документах).
- Інтерактивний прототип екранів налаштувань і входу — стандартні форми.
- RTL-мови.

## 5. Trade-offs accepted

- **Contract із запізненням на вікно.** Старі колонки живуть до 3 місяців на production — це
  ціна відкату без DDL.
- **Розробники мусять розділяти expand і contract** і писати міграції як надмножину. microrun
  ловить порушення, але не виправляє їх.
- **Diff MongoDB слабший за SQL:** бачить колекції, індекси й валідатори, але не форму
  документів.
- **На не-production оточеннях** (`post_check`) деструктивна міграція вже застосована, коли
  microrun її помічає: деплой зупиняється, але дані можуть бути втрачені. Свідомо — dry-run
  на кожному оточенні дорогий; режим перемикається в налаштуваннях.
- **Кількість у прибиранні повідомляє скрипт розробника**; microrun лише фіксує розбіжність.
- **Доступ до `docker.sock`** рівнозначний root на хості — і для вбудованого, і для зовнішнього агента.
- **microrun не знає графа git.** Старий коміт, якого microrun не бачив, або пайплайн, що
  завершився не по черзі, деплояться як нові; захищають від цього dry-run/порівняння схеми й
  блокування після відкату, але не порядок комітів.
- **Дозвіл деструктивної зміни** робить усі доступні релізи оточення простроченими — відкат
  через таку зміну неможливий за визначенням.
- **Ручний `docker compose up` без override-файлу** поверне образ із compose-файлу, а не активний
  реліз; документація про це попереджає.
- **SQLite як база застосунку з rolling:** два контейнери пишуть в один файл під час заміни —
  потрібен WAL-режим у застосунку.

  піднімає UI на `:8080`; вхід з ENV-обліковими даними працює, з неправильними — ні.
- `npm i -g microrun && microrun agent --url … --token …` — сервер у UI стає «онлайн» без
  відкритих вхідних портів на хості агента.
- Повторний `microrun deploy` заблокованого коміту завершується з exit 2 і повідомленням, що
  містить `COMMIT_BLOCKED`, коміт і дату відкату.
- Прив'язка бази, вже прив'язаної до іншого оточення, відхиляється з назвою того оточення.
